# Phase 10-04 — Thread AnalysisReport into Video Job

## Goal

When the user clicks "Create Video" from an analysis result, the video job
dispatcher reads the persisted `AnalysisReport` from the DB and passes the
hook, pacing, structure, and style insights into `download_and_process_task`
as `analysis_data`. The job record also stores an `analysis_snapshot` in
`job_metadata` for traceability.

## Why it matters

- **Close the loop**: Analysis insights actually influence video generation
  (pacing, style, hook strategy) instead of being thrown away.
- **Backward compatible**: Celery fallback path still works; the new fields
  are additive.
- **Traceability**: Every video job carries `analysis_snapshot` in its
  metadata so debugging/re-audit is possible.

## Success Criteria

1. `create_video_from_analysis` reads the `AnalysisReport` from
   `ContentCandidateDB.analysis_payload` (same path as 10-03 endpoint).
2. When the DB report is available, `download_and_process_task` receives
   `analysis_data` containing both a legacy-compatible `pattern` dict and
   a rich `analysis_report` dict.
3. When the DB report is NOT available (legacy Celery result only), the
   existing behavior is unchanged — `analysis_data` is None.
4. `strategy_service.generate_visual_strategy` uses the `analysis_report`
   fields when present (hook insights, pacing, structure, style, sentiment)
   to inform the visual strategy LLM prompt.
5. `job_metadata.analysis_snapshot` is stored in the `VideoJobDB` record
   via `extra_metadata`.
6. Unit tests cover: analysis_data shape, analysis_snapshot in job metadata,
   backward-compatible Celery fallback.
